# Nubra Dashboard performance plan

16 November 2026

Make both modes as light as practical using one fresh Nubra Dashboard build. **PC mode** preserves the current appearance and normal throughput while reducing load and stutter. **Laptop mode** targets the roughly 10-year-old Pentium with 2 GB of RAM. It may simplify decoration or queue background jobs more conservatively. Both modes preserve every feature, input, control, accessible workflow, chart resolution, data detail, quote freshness, execution behavior, and analysis result. Keep the same API and persisted data paths.

The static audit covered HEAD `e1ce1374` and in-progress Trade Explorer and Signal Backtest edits. The earlier light-PC pass is recorded in `2c9de877`. Baseline measurements, builds, and tests are pending. This revision changes the plan only.

## Unit 0 — Check the production build on both machines

1. **Identify the build.** Record the revision, working-tree state, and hash of a fresh production `dist` from a dedicated copy. Use the same build for both machines. The current `npm start` runs Fastify and Vite. `npm run start:light` runs Fastify alone and selects no mode. Fastify serves `dist` when present. Preserve the live build and session. Verify browser origin and data continuity before changing daily launch habits. Port or hostname changes can expose different localStorage and IndexedDB state. [Scripts](../package.json#L6), [static assets](../server/index.ts#L570), [workspace storage](../src/workspace/useWorkspaceState.ts#L23), [IndexedDB](../src/db.ts#L15).
2. **Current PC.** Compare routine use under the existing launch and the production-only launch. Include cold start, connected idle, and several normal interactions during live updates. Measure chart pan and crosshair, chain scrolling, expiry selection and the usual split or historical work. Record the workspace, browser, display refresh rate, and other open apps.
3. **Pentium laptop.** The user reports that regular startup fails and a lightweight launch opens but becomes laggy. Verify which command and build they used. Capture the regular startup error once if feasible, then focus on reproducing lag in the working launch. Compare connected idle with chart and chain interaction in one live workspace. Trace browser main-thread frame work and correlate stalls with Node and browser CPU, available RAM, hard faults and disk activity. Try the fresh prebuilt production candidate if the working launch differs. Record exact CPU, available RAM, OS version, browser, GPU and HDD or SSD. Once the short run is usable, run the 60-minute acceptance case. Assess split layouts, live plus historical work, and the largest expected datasets separately.
4. **Collect proportionate evidence.** Start with Task Manager for Node and browser CPU, memory, GPU and disk activity. Take one short Chrome Performance trace per relevant workload for missed frames, long tasks, and input-to-paint. Check system commit, available memory, hard faults and paging I/O when the laptop stalls. Use Node `--cpu-prof` only if Node CPU is implicated. Repeat close or variable comparisons. Future read-only live observation can inform the baseline. Use isolated fixtures for mutations, with dedicated ports, browser profiles, session files and databases. [Session path](../server/index.ts#L220).

**PC gate.** Confirm repeatable gains beyond normal variation in CPU, retained memory, interaction latency or missed frames. Preserve the original screenshots across themes and layouts, normal historical throughput, quote freshness and application behavior.

**Laptop gate.** Set a combined app memory budget from measured OS, background-app and shared-GPU headroom, with room for peaks. Require no crashes, out-of-memory events or sustained paging associated with stalls during the hour. Provisional targets are p95 frame intervals of about 33 ms or less at 60 Hz during continuous actions and p95 input-to-paint of 150 ms or less for discrete actions. Check idle memory settles and validate quote freshness and workflow parity. Report each heavier workload separately, including job turnaround.

## Unit 1 — Apply the measured mode and resource changes

Propose `NUBRA_MODE=pc|laptop` at startup with PC as the existing-default path. Resolve it once and report the effective mode. Both modes can use the same production assets, origin, and database. Add browser/server agreement if browser cache, prefetch or styling needs the selection. Verify PC → Laptop → PC against the same origin and database, including workspace and chart settings, saved records and paper state. Cross-device synchronization is outside scope.

- **Laptop concurrency first if CPU contention appears.** Check effective `availableParallelism()` and any override. The Parquet worker default is `max(1, min(8, cores - 2))`, so the laptop may already use one worker. Try the existing `SIGNAL_PARQUET_WORKERS` override if justified. Measure completion time, foreground responsiveness and memory. Consider bounded concurrency for overlapping historical jobs while retaining complete results. Under measured memory pressure, a V8 heap limit is a bounded experiment. It can increase GC or OOM and does not cap browser, SQLite or Buffer memory. [Worker selection](../server/signalBacktest/ohlc.ts#L70).
- **Cache retention if memory grows.** Shared-request TTL controls reuse. Fulfilled unique keys can retain expired Greek history responses until replacement or explicit invalidation. Confirm in heap captures. Existing local Backtest, Analysis, Signal Backtest and Explorer limits are hardcoded entry counts in several places. Tighter Laptop budgets, estimated-byte eviction and less speculative prefetch need targeted code. Keep on-demand data, inflight sharing, retries, source and generation invalidation. Check stale completion and cold reopen. [Shared requests](../src/lib/sharedRequest.ts#L25), [local cache](../server/backtest/dataLayer.ts#L67), [Analysis cache](../server/analysis/routes.ts#L169), [Signal Backtest](../server/signalBacktest/routes.ts#L403), [Explorer prefetch](../src/lib/explorerCache.ts#L94).
- **Laptop paint if evidence warrants it.** Trace actual themes. Flatten decorative surfaces, replace nonessential animation with clear static feedback, or simplify costly blur, shadows and gradients where measured. Preserve semantic colors, contrast, focus, chart resolution and every control. Compare PC screenshots with the originals and Laptop screenshots with its approved appearance. An optional GPU acceleration A/B holds the workload and other settings fixed. [Status pulse](../src/index.css#L91), [backdrop blur](../src/index.css#L843), [data styling](../src/tradeExplorer.css#L291).

## Unit 2 — Fix confirmed hotspots and remeasure

Take the highest-impact one to three confirmed items first. Measure after each narrow change. Continue while either gate misses or a material, safe savings candidate remains.

| Trace finding | Candidate and parity check |
| --- | --- |
| Chain, Greeks or resize blocks paint | Reuse OI nodes and change only text or widths that differ. Preserve OI scale, expiry changes and feed health. Use incremental Greek/IV tail updates only when equivalent to full redraw. Coalesce pointer resizing with the same final geometry and keyboard behavior. [Chain](../src/OptionChain.tsx#L533), [Greek renderer](../src/lib/greekRenderer.ts#L374), [dividers](../src/workspace/SplitDivider.tsx). |

Use worker isolation for historical work only after measuring transfer cost and exact result parity. [Relay](../server/index.ts#L1028), [SimBroker](../server/simBroker.ts#L204). |

## Verification and release

Use focused checks, `npm run typecheck`, `npm test` and `npm run build` for implementation changes. Check frontend interaction, visuals, keyboard focus and readability in both modes. Before touching relay, feed or order-rule logic, add deterministic isolated replay for mixed exchanges, multiple tabs, stale and partial ticks, disconnects, stops, targets, time exits and exact paper events and paise values. Compare complete historical outputs and ordering for changes to historical processing or caches. Keep each change independently reviewable and revertible. Consider a separate host only if local gates miss and the user expands scope. The current API lacks caller authentication, so remote access requires an auth and network design before changing the binding. [Server binding](../server/index.ts#L156).
